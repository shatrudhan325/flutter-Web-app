API Integration
Theory

A clean API layer separates three concerns: the data model (parsing JSON into Dart objects), the service/repository (making the actual HTTP call), and the UI (consuming the result via a state management layer). This separation makes it easy to swap the backend, mock the network for tests, and handle errors consistently.

api_integration.dart
// ── MODEL ──────────────────────────────
class User {
  final int id;
  final String name;
  User({required this.id, required this.name});

  factory User.fromJson(Map<String, dynamic> json) =>
      User(id: json['id'], name: json['name']);
}

// ── SERVICE LAYER ──────────────────────
class UserService {
  final Dio _dio;
  UserService(this._dio);

  Future<User> getUser(int id) async {
    final res = await _dio.get('/users/$id');
    return User.fromJson(res.data);
  }
}

// ── REPOSITORY — adds caching/error mapping ──
class UserRepository {
  final UserService _service;
  UserRepository(this._service);

  Future<User> fetchUser(int id) async {
    try {
      return await _service.getUser(id);
    } on DioException catch (e) {
      throw Exception('Failed to load user: ${e.message}');
    }
  }
}
🎯 Interview Question
Q: Why separate Service and Repository layers instead of calling Dio directly from the UI?
It keeps networking details out of widgets, makes the data layer mockable for unit tests (swap a fake repository in), and centralizes error transformation and caching logic in one place instead of repeating it across every screen that needs data.

JWT Authentication
Theory

JWT (JSON Web Token) auth typically issues a short-lived access token and a longer-lived refresh token. The access token is sent with every request (usually in the Authorization header); when it expires (401 response), the app silently uses the refresh token to get a new access token, without forcing the user to log in again. Tokens should be stored in secure storage, never plain SharedPreferences, since they're sensitive credentials.

jwt_auth.dart
dio.interceptors.add(InterceptorsWrapper(
  onRequest: (options, handler) async {
    final token = await secureStorage.read(key: 'access_token');
    options.headers['Authorization'] = 'Bearer $token';
    handler.next(options);
  },
  onError: (error, handler) async {
    if (error.response?.statusCode == 401) {
      final refreshToken = await secureStorage.read(key: 'refresh_token');
      final res = await dio.post('/refresh', data: {'token': refreshToken});
      await secureStorage.write(key: 'access_token', value: res.data['access_token']);

      // retry the original request with the new token
      final retryResponse = await dio.fetch(error.requestOptions);
      return handler.resolve(retryResponse);
    }
    handler.next(error);
  },
));
🎯 Interview Question
Q: Why use flutter_secure_storage instead of SharedPreferences for tokens?
SharedPreferences stores values in plain text (XML on Android, plist on iOS) — accessible if the device is rooted/jailbroken or backed up insecurely. flutter_secure_storage uses Android's Keystore and iOS's Keychain, which encrypt the data at the OS level — the appropriate place for sensitive credentials like JWTs.

SharedPreferences
Theory

SharedPreferences is a simple, asynchronous key-value store for small, non-sensitive data — things like a "remember theme mode" flag, onboarding-seen flag, or last-selected tab. It's not meant for structured data, large datasets, or anything sensitive (use Hive/Sqflite or secure storage for those instead).

shared_prefs.dart
void saveOnboardingSeen() async {
  final prefs = await SharedPreferences.getInstance();
  await prefs.setBool('onboarding_seen', true);
  await prefs.setString('theme_mode', 'dark');
  await prefs.setInt('last_tab_index', 2);
}

Future<bool> hasSeenOnboarding() async {
  final prefs = await SharedPreferences.getInstance();
  return prefs.getBool('onboarding_seen') ?? false;
}
🎯 Interview Question
Q: Why would you avoid storing a list of complex objects in SharedPreferences?
SharedPreferences only natively supports primitives (bool, int, double, String, List<String>) — anything more complex needs manual JSON encode/decode on every read/write, which is slow and error-prone at scale. Hive or Sqflite are built for structured/larger data and handle serialization more efficiently.

Hive
Theory

Hive is a fast, pure-Dart NoSQL key-value database that works without native dependencies — making it faster to set up than Sqflite and well suited for storing Dart objects directly via generated TypeAdapters. Data is organized into boxes (similar to tables), and reads/writes are synchronous after the box is opened, which is a notable performance advantage over Sqflite's always-async API.

hive.dart
// ── MODEL with generated adapter ───────
@HiveType(typeId: 0)
class Task extends HiveObject {
  @HiveField(0)
  final String title;
  @HiveField(1)
  final bool isDone;

  Task({required this.title, this.isDone = false});
}

// ── SETUP & USAGE ───────────────────────
void main() async {
  await Hive.initFlutter();
  Hive.registerAdapter(TaskAdapter());
  final box = await Hive.openBox<Task>('tasks');

  box.add(Task(title: 'Finish Flutter notes'));
  final tasks = box.values.toList();   // synchronous read!
}
🎯 Interview Question
Q: When would you choose Hive over Sqflite?
Choose Hive for simpler key-value/object storage needs where you don't need complex relational queries or joins — it's faster to set up (no SQL, no native plugin compilation issues) and offers synchronous reads. Choose Sqflite when you have genuinely relational data with multiple linked tables and need SQL-level querying, filtering, and aggregation.

Sqflite
Theory

Sqflite gives you a full SQLite database on-device — ideal when your local data is genuinely relational (e.g. orders linked to customers linked to products) and you need real SQL queries, joins, and transactions. Migrations are handled via the onUpgrade callback, keyed off a database version number.

sqflite.dart
final db = await openDatabase(
  'app.db',
  version: 1,
  onCreate: (db, version) async {
    await db.execute('''
      CREATE TABLE users(
        id INTEGER PRIMARY KEY,
        name TEXT,
        age INTEGER
      )
    ''');
  },
);

// ── INSERT ───────────────────────────────
await db.insert('users', {'name': 'Shatrudhan', 'age': 23});

// ── QUERY ────────────────────────────────
final users = await db.query('users', where: 'age > ?', whereArgs: [18]);

// ── UPDATE ───────────────────────────────
await db.update('users', {'age': 24}, where: 'id = ?', whereArgs: [1]);
🎯 Interview Question
Q: How do you handle a schema migration in Sqflite?
Bump the version parameter in openDatabase and implement the onUpgrade callback, which receives the old and new version numbers. Inside, run the appropriate ALTER TABLE/CREATE TABLE statements conditionally based on which version the user is upgrading from, so existing user data isn't lost.

Firebase
Theory

Firebase is Google's backend-as-a-service suite. The most commonly used pieces in Flutter apps are Firebase Auth (email/phone/social sign-in), Firestore (a NoSQL document database with real-time listeners), Cloud Storage (file uploads), and Cloud Messaging/FCM (push notifications, see Chapter 22). It removes the need to build a custom backend for many common app needs.

firebase.dart
// ── AUTH ─────────────────────────────────
final cred = await FirebaseAuth.instance.signInWithEmailAndPassword(
  email: email, password: password,
);

// ── FIRESTORE — write & real-time listen ──
await FirebaseFirestore.instance
    .collection('users')
    .doc(cred.user!.uid)
    .set({'name': 'Shatrudhan', 'plan': 'pro'});

FirebaseFirestore.instance
    .collection('users')
    .doc(uid)
    .snapshots()                        // real-time stream of changes
    .listen((snapshot) => print(snapshot.data()));
🎯 Interview Question
Q: What's the tradeoff of using Firestore instead of a custom REST backend?
Firestore gives you real-time sync, offline persistence, and scaling out of the box with very little backend code — great for MVPs and many production apps. The tradeoff is less control over complex relational queries/joins (it's a NoSQL document store), vendor lock-in to Google's pricing model, and security rules replacing traditional server-side business logic, which has its own learning curve.

Notifications
Theory

There are two kinds of mobile notifications: local notifications (scheduled/triggered from inside the app itself, e.g. a reminder) using flutter_local_notifications, and push notifications sent from a server via Firebase Cloud Messaging (FCM), which work even when the app is closed.

notifications.dart
// ── LOCAL NOTIFICATION ──────────────────
final notifications = FlutterLocalNotificationsPlugin();

await notifications.show(
  0, 'Reminder', 'Standup at 10 AM',
  NotificationDetails(
    android: AndroidNotificationDetails('channel_id', 'General'),
  ),
);

// ── FCM PUSH — listen for messages ───────
FirebaseMessaging.onMessage.listen((RemoteMessage message) {
  print('Foreground push: ${message.notification?.title}');
});

// ── Get device token to send TO this device ──
final token = await FirebaseMessaging.instance.getToken();
🎯 Interview Question
Q: Why do you need a separate handler for background/terminated FCM messages?
FirebaseMessaging.onMessage only fires while the app is in the foreground. For background or terminated states, you must register a top-level (or static) onBackgroundMessage handler, since Dart isolates handling background messages run in a separate, limited execution context without access to the running app's widget tree.

Deep Linking
Theory

Deep links let an external link (a URL, push notification, or another app) open your Flutter app directly to a specific screen. Custom schemes (myapp://product/42) are simplest but not verifiable; App Links (Android) and Universal Links (iOS) use real HTTPS URLs verified against your domain, which is the production-grade approach. Routers like go_router parse the incoming URI and navigate accordingly.

deep_linking.dart
// go_router automatically handles incoming deep links
// matching a registered route pattern:
final router = GoRouter(
  routes: [
    GoRoute(
      path: '/product/:id',
      builder: (context, state) {
        final id = state.pathParameters['id']!;
        return ProductPage(productId: id);
      },
    ),
  ],
);

// https://trinetra.app/product/42 (App Link) or
// myapp://product/42 (custom scheme) both resolve here
// once configured in AndroidManifest.xml / Info.plist.
🎯 Interview Question
Q: Why are App Links / Universal Links preferred over custom URL schemes in production?
A custom scheme like myapp:// can be claimed by any app, creating a hijacking risk and ambiguity when multiple apps register the same scheme. App Links/Universal Links are cryptographically verified against your real domain (via a hosted JSON file), so the OS only opens your app for those URLs — and if your app isn't installed, the link gracefully falls back to opening in a browser.

Responsive UI
Theory

Flutter doesn't have native "breakpoints" — you build responsiveness yourself using MediaQuery (read screen size/orientation), LayoutBuilder (react to a parent's available constraints, not just the whole screen), and flexible layout widgets (Expanded, Flexible, FittedBox) instead of fixed pixel sizes.

responsive.dart
// ── LayoutBuilder — react to AVAILABLE space, not screen size ──
LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth > 600) {
      return _WideLayout();
    }
    return _NarrowLayout();
  },
);

// ── MediaQuery — full screen metrics ────
final size = MediaQuery.of(context).size;
final isTablet = size.width > 600;

// ── Flexible sizing instead of fixed px ──
Row(children: [
  Expanded(flex: 2, child: Sidebar()),
  Expanded(flex: 5, child: Content()),
]);
🎯 Interview Question
Q: What's the difference between MediaQuery.size and LayoutBuilder's constraints?
MediaQuery.of(context).size reflects the entire device screen, regardless of where in the widget tree you are. LayoutBuilder gives the actual constraints passed down by its immediate parent — crucial when a widget is nested inside something like a side panel or a grid cell, where the available space is much smaller than the full screen.

Performance Optimization
Theory

The most common performance wins in Flutter come from reducing unnecessary rebuilds and repaints: using const constructors, ListView.builder for long lists (lazy-builds only visible items instead of all at once), RepaintBoundary to isolate expensive paints, and avoiding heavy work inside build(). Flutter DevTools' "repaint rainbow" and timeline view are the standard tools to diagnose jank.

performance.dart
// ── BAD: builds ALL 10,000 items upfront ──
ListView(children: items.map((i) => ItemTile(item: i)).toList());

// ── GOOD: lazily builds only visible items ──
ListView.builder(
  itemCount: items.length,
  itemBuilder: (context, index) => ItemTile(item: items[index]),
);

// ── RepaintBoundary — isolate expensive paint ──
RepaintBoundary(
  child: CustomPaint(painter: ExpensiveChartPainter()),
);

// ── const everywhere possible ────────────
const SizedBox(height: 16);   // no rebuild needed, ever
🎯 Interview Question
Q: How would you debug a janky scrolling list?
First switch to ListView.builder if not already used. Then open Flutter DevTools' Performance tab to look for frames exceeding 16ms (the 60fps budget), enable the "repaint rainbow" to spot widgets repainting unnecessarily, and wrap expensive custom paints in RepaintBoundary so they don't get redrawn just because a sibling widget changed.

Animations
Theory

Flutter has two animation styles. Implicit animations (AnimatedContainer, AnimatedOpacity) automatically tween between old and new property values whenever they change — minimal code, limited control. Explicit animations use an AnimationController + Tween for full control over duration, curve, and playback (forward, reverse, repeat). Hero widgets animate a shared element between two pages during navigation.

animations.dart
// ── IMPLICIT — simplest, auto-tweens ────
AnimatedContainer(
  duration: Duration(milliseconds: 300),
  width: _expanded ? 200 : 100,
  color: _expanded ? Colors.blue : Colors.grey,
);

// ── EXPLICIT — full control ─────────────
class _PulseState extends State<Pulse> with SingleTickerProviderStateMixin {
  late final _controller = AnimationController(
    vsync: this, duration: Duration(seconds: 1),
  )..repeat(reverse: true);
  late final _scale = Tween(begin: 1.0, end: 1.2).animate(_controller);

  @override
  void dispose() { _controller.dispose(); super.dispose(); }

  @override
  Widget build(BuildContext context) =>
      ScaleTransition(scale: _scale, child: Icon(Icons.favorite));
}

// ── HERO — shared element transition ────
Hero(tag: 'product-image', child: Image.network(url));
🎯 Interview Question
Q: Why must you dispose an AnimationController?
An AnimationController holds a Ticker that registers itself with the engine to receive a callback on every frame. If you don't dispose it when the widget is removed, that ticker keeps firing against a dead widget, leaking memory and potentially throwing "a ticker was disposed twice" or "Ticker was used after... was disposed" errors.

Custom Painter
Theory

CustomPainter gives direct access to a Canvas for drawing arbitrary shapes, paths, and effects that built-in widgets can't express — charts, signature pads, custom progress indicators. The shouldRepaint method controls whether the canvas is redrawn on rebuild, which is critical for performance since painting can be expensive.

custom_painter.dart
class CirclePainter extends CustomPainter {
  final double progress;
  CirclePainter(this.progress);

  @override
  void paint(Canvas canvas, Size size) {
    final paint = Paint()
      ..color = Colors.blue
      ..strokeWidth = 8
      ..style = PaintingStyle.stroke;

    final center = Offset(size.width / 2, size.height / 2);
    canvas.drawArc(
      Rect.fromCircle(center: center, radius: 50),
      -1.57, 6.28 * progress, false, paint,
    );
  }

  @override
  bool shouldRepaint(CirclePainter old) => old.progress != progress;
}

// usage
CustomPaint(size: Size(120, 120), painter: CirclePainter(0.7));
🎯 Interview Question
Q: Why does shouldRepaint matter for performance?
Returning true unconditionally forces a full repaint on every frame even when nothing visually changed — wasteful for static or rarely-changing custom paints. Comparing the relevant fields between old and new painter instances lets Flutter skip expensive canvas redraws when the actual visual output wouldn't change.

Clean Architecture
Theory

Clean Architecture organizes code into concentric layers with a strict dependency rule: inner layers never depend on outer layers. The Domain layer (entities, use cases, repository interfaces) is pure Dart with zero Flutter or package imports. The Data layer implements those repository interfaces using real APIs/databases. The Presentation layer (widgets, state management) depends on Domain, never directly on Data — keeping business logic testable and swappable.

clean_architecture.dart
// ── DOMAIN LAYER — pure Dart, no Flutter import ──
abstract class UserRepository {
  Future<User> getUser(int id);    // interface only
}

class GetUserUseCase {
  final UserRepository repository;
  GetUserUseCase(this.repository);
  Future<User> call(int id) => repository.getUser(id);
}

// ── DATA LAYER — implements the interface ──────
class UserRepositoryImpl implements UserRepository {
  final Dio dio;
  UserRepositoryImpl(this.dio);

  @override
  Future<User> getUser(int id) async {
    final res = await dio.get('/users/$id');
    return User.fromJson(res.data);
  }
}

// ── PRESENTATION — depends on Domain, never Data ──
final useCase = GetUserUseCase(UserRepositoryImpl(dio)); // injected at the edge
🎯 Interview Question
Q: How would you unit test the GetUserUseCase without hitting a real API?
Because UserRepository is an abstract interface, you create a fake/mock implementation (e.g. with mocktail) that returns a hardcoded User instead of calling Dio. The use case never knows the difference — that's exactly the point of depending on abstractions rather than concrete implementations.

Testing
Theory

Flutter testing has three levels. Unit tests verify a single function/class in isolation (fast, no Flutter engine needed). Widget tests pump a widget into a simulated environment and verify rendering/interaction without a real device. Integration tests run on a real device/emulator, testing full user flows end-to-end. Mocking (e.g. with mocktail) isolates the unit under test from real network/database calls.

testing.dart
// ── UNIT TEST ───────────────────────────
test('GetUserUseCase returns user from repository', () async {
  final mockRepo = MockUserRepository();
  when(() => mockRepo.getUser(1)).thenAnswer((_) async => User(id: 1, name: 'Shatrudhan'));

  final useCase = GetUserUseCase(mockRepo);
  final user = await useCase(1);

  expect(user.name, 'Shatrudhan');
});

// ── WIDGET TEST ─────────────────────────
testWidgets('Counter increments on tap', (WidgetTester tester) async {
  await tester.pumpWidget(MaterialApp(home: CounterWidget()));
  expect(find.text('Count: 0'), findsOneWidget());

  await tester.tap(find.text('+'));
  await tester.pump();        // rebuild after the tap
  expect(find.text('Count: 1'), findsOneWidget());
});
🎯 Interview Question
Q: What's the difference between tester.pump() and tester.pumpAndSettle()?
pump() triggers exactly one frame rebuild — useful right after an action like a tap when you know one rebuild is enough. pumpAndSettle() repeatedly pumps frames until there are no more scheduled frames (e.g. waiting out an animation) — necessary when the UI change involves a transition or async delay, but it can time out if something keeps scheduling frames indefinitely.

Advanced Interview Questions — Rapid Fire
Theory

A compiled set of advanced/scenario-based Flutter questions commonly asked in senior or "machine coding" rounds — useful for a final review pass.

Q: How would you reduce app startup time?
Defer heavy initialization (analytics SDKs, non-critical Firebase modules) until after the first frame using WidgetsBinding.instance.addPostFrameCallback, lazy-load feature modules, minimize work in main() before runApp(), and use deferred imports for rarely-used large packages.
Q: Explain the difference between hot reload and hot restart.
Hot reload injects updated code into the running Dart VM and re-runs build(), preserving app state (e.g. current screen, form input) — fast but doesn't pick up changes to main(), global variables, or native code. Hot restart fully restarts the Dart VM and app from scratch, losing state but applying all changes including initialization logic.
Q: How do InheritedWidget and Provider relate?
Provider is built directly on top of InheritedWidget — it's a more ergonomic API around the same underlying mechanism that lets descendant widgets efficiently look up data from an ancestor without explicit prop drilling, and rebuild only when that specific data changes.
Q: What is tree shaking icons / fonts and why does it matter?
Flutter can tree-shake unused icons out of icon font packages (like MaterialIcons) at build time if it can statically determine which icons are referenced, significantly reducing release app size — this is why dynamically-constructed icon codepoints (e.g. from a remote config) can break shaking and bloat the binary.
Q: How would you architect offline-first behavior in a Flutter app?
Treat the local database (Hive/Sqflite) as the single source of truth that the UI always reads from. Sync with the remote API in the background — queue writes locally when offline and replay them on reconnect (often using a "pending sync" flag per record), and use a connectivity listener to trigger sync attempts.
Q: What's the purpose of the const constructor optimization in large widget trees?
A const widget subtree is built exactly once at compile time. When an ancestor rebuilds, Flutter recognizes the const child as identical (same instance) and skips rebuilding/diffing it entirely — for deeply nested static UI (icons, padding, dividers), this avoids a meaningful amount of redundant work on every frame.
