Variables
Theory

Dart gives you four ways to declare a variable: var (type inferred, reassignable), final (set once at runtime), const (compile-time constant, deeply immutable), and late (non-nullable but initialized after declaration). Choosing the right one signals intent and helps the compiler catch bugs early.

variables.dart
void main() {
  // var — inferred type, reassignable
  var name = 'Shatrudhan';
  name = 'Kumar';           // ✓ OK

  // final — set once, runtime value allowed
  final age = 23;
  // age = 24;             // ✗ Error: can't assign to final

  // const — compile-time, deeply immutable
  const pi = 3.14159;

  // late — non-nullable but assigned later
  late String token;
  token = fetchToken();  // assigned before use ✓
}
🎯 Interview Question
Q: Can you use a function call to assign a const variable?
No. const must be a compile-time constant. Use final if the value comes from a function or is computed at runtime.

Data Types
Theory

Everything in Dart is an object — even numbers and functions. Built-in types include num (parent of int and double), String, bool, and the collection types List, Set, Map. Dart is statically typed but supports type inference via var.

int

Whole numbers, 64-bit on native platforms.

double

64-bit floating-point numbers.

num

Parent type of int & double — useful for generic math.

String

UTF-16 sequence, immutable, supports interpolation.

bool

Strictly true/false — no truthy/falsy values like JS.

dynamic

Bypasses static type checking — use sparingly.

data_types.dart
void main() {
  int age = 23;
  double price = 499.99;
  num anyNumber = age;        // num accepts int or double
  bool isActive = true;

  // ── STRING INTERPOLATION ─────────────
  String name = 'Shatrudhan';
  print('Hi $name, age: ${age + 1}');

  // ── TYPE CONVERSION ──────────────────
  String ageStr = age.toString();
  int parsed = int.parse('42');
  double d = double.parse('3.14');
  int? safe = int.tryParse('abc'); // null, no crash

  // ── STRING METHODS ───────────────────
  print('  hi  '.trim());          // 'hi'
  print('hi,bye'.split(','));    // [hi, bye]
  print('hi'.toUpperCase());    // HI
}
🎯 Interview Question
Q: Why prefer int.tryParse over int.parse?
int.parse throws a FormatException on invalid input, crashing the app if unhandled. int.tryParse returns null instead, which is safer for user input like form fields.

Null Safety
Theory

Dart's sound null safety means the compiler guarantees non-nullable variables never contain null — caught at compile time, not runtime. Nullable types are explicitly marked with ?, making nullability visible and intentional.

✓ Non-Nullable (Default)
String name = 'Alice';
// name can NEVER be null
? Nullable (Explicit)
String? name;
// must handle null case
null_safety.dart
void main() {
  String? name;
  print(name ?? 'Guest');         // Guest
  name ??= 'Default';
  print(name?.length);          // safe access

  User? user = getUser();
  if (user != null) {
    print(user.name);          // smart-promoted, no ! needed
  }
}
🎯 Interview Question
Q: When is it safe to use the ! null assertion operator?
Only when you're certain the value is non-null at that point — e.g., right after a null check, or with late-initialized fields you control. Overusing ! defeats the purpose of null safety and reintroduces runtime crashes.

Functions
Theory

Functions in Dart are first-class objects — they can be assigned to variables, passed as arguments, and returned from other functions. Dart supports positional, named, and optional parameters, arrow syntax for one-liners, and closures that capture variables from their surrounding scope.

Positional

fn(String a, int b) — order matters.

Optional Positional

fn(String a, [int? b]) — wrapped in [].

Named

fn({required String a, int b = 0}) — wrapped in {}.

Closure

A function that captures variables from its enclosing scope.

functions.dart
// ── NAMED & OPTIONAL PARAMS ───────────
String greet({required String name, String greeting = 'Hello'}) {
  return '$greeting, $name!';
}
print(greet(name: 'Shatrudhan'));        // Hello, Shatrudhan!

// ── OPTIONAL POSITIONAL ───────────────
int add(int a, [int b = 0]) => a + b;

// ── ARROW FUNCTION ────────────────────
int square(int n) => n * n;

// ── CLOSURE — captures surrounding scope ──
Function counter() {
  int count = 0;
  return () {
    count++;
    return count;
  };
}
void main() {
  final increment = counter();
  print(increment());   // 1
  print(increment());   // 2 — count persists across calls

  // function passed as a parameter (higher-order)
  [1,2,3].forEach((n) => print(square(n)));
}
🎯 Interview Question
Q: What's the difference between optional positional [ ] and named { } parameters?
Optional positional params are passed by position and wrapped in [] — order matters, no labels at the call site. Named params are wrapped in {}, passed by name in any order, and are self-documenting — generally preferred for readability when a function has 3+ parameters.

Collections
Theory

Dart has three built-in collection types: List (ordered, indexed), Set (unique elements), and Map (key-value pairs). All support generics for type safety. Dart also has collection literals with control flow — if, for, and spread (...) inside collections.

collections.dart
// ── LIST ─────────────────────────────
List<String> fruits = ['apple', 'mango', 'banana'];
fruits.add('grapes');
print(fruits[0]);

// ── SET ──────────────────────────────
Set<int> ids = {1, 2, 3, 2};
print(ids);  // {1, 2, 3} — duplicates removed

// ── MAP ──────────────────────────────
Map<String, int> scores = {'Alice': 95, 'Bob': 80};
scores['Charlie'] = 90;

// ── SPREAD & COLLECTION CONTROL ──────
final extra = [4, 5];
final all   = [1, 2, 3, ...extra];
bool isAdmin = true;
final menu  = [
  'Home',
  if (isAdmin) 'Admin Panel',
  for (var i in [1,2]) 'Item $i',
];
🎯 Interview Question
Q: When would you use Set over List?
Use Set when you need unique elements and don't care about order — lookup is O(1) vs O(n) in List. Use List when order matters or duplicates are allowed.

06 / 20
OOP
Theory

Dart is fully object-oriented — everything is an object. It supports all four OOP pillars: Encapsulation (_ prefix for private), Inheritance (extends), Polymorphism (@override), and Abstraction (abstract). Dart has no interface keyword — every class implicitly defines an interface that can be implemented with implements.

Encapsulation

Hide state with _ prefix. Expose via getters/setters.

Inheritance

extends for is-a relationships. Single inheritance only.

Polymorphism

Override with @override — same method, different behavior.

Abstraction

abstract class defines a contract, can't be instantiated.

implements

Enforce a contract as an interface — must implement ALL members.

factory

Constructor returning a subtype/cached instance. See Ch.17.

oop.dart
abstract class Animal {
  void makeSound();
  void breathe() => print('Breathing');
}

class Dog extends Animal {
  final String name;
  Dog(this.name);

  @override
  void makeSound() => print('$name says Woof!');
}

class User {
  final String name;
  User(this.name);
  User.guest() : name = 'Guest';     // named constructor
}
🎯 Interview Question
Q: Why does Dart not have a separate "interface" keyword?
Every Dart class implicitly defines an interface consisting of its instance members. Any class can implements another class to satisfy that interface, without needing a dedicated interface keyword like Java.

Generics
Theory

Generics let you write reusable, type-safe code without duplicating logic per type. Instead of using dynamic (which loses compile-time checks), a generic type parameter like <T> lets the compiler enforce consistency while keeping the implementation generic.

generics.dart
// ── GENERIC CLASS ─────────────────────
class Box<T> {
  final T value;
  Box(this.value);
}
final intBox = Box<int>(42);
final userBox = Box<User>(User('Shatrudhan'));

// ── GENERIC METHOD ────────────────────
T first<T>(List<T> items) => items[0];

// ── BOUNDED GENERIC ───────────────────
T largest<T extends num>(T a, T b) => a > b ? a : b;
print(largest(3, 7));      // works only with num subtypes
🎯 Interview Question
Q: Why use generics instead of dynamic?
dynamic disables compile-time type checking entirely — bugs surface only at runtime. Generics keep the implementation reusable across types while preserving full compile-time safety and IDE autocomplete.

Extensions
Theory

Extensions let you add new methods, getters, and setters to existing types — even SDK types like String or int — without modifying their source code or wrapping them in a subclass. They're resolved statically, so they don't add runtime overhead.

extensions.dart
extension StringUtils on String {
  bool get isValidEmail => contains('@') && contains('.');

  String get capitalize =>
      isEmpty ? this : this[0].toUpperCase() + substring(1);
}

extension IntUtils on int {
  bool get isEven => this % 2 == 0;
  Duration get seconds => Duration(seconds: this);
}

// Usage — feels like built-in methods!
print('hello'.capitalize);               // Hello
print('dev@mail.com'.isValidEmail);      // true
await Future.delayed(2.seconds);         // wait 2 seconds
🎯 Interview Question
Q: Do extensions let you override existing methods on a type?
No. If a member name in your extension collides with a member already on the class, the class's own member wins. Extensions only add new members — they cannot override existing behavior, which prevents conflicts across libraries.

Mixins
Theory

Mixins solve the "diamond problem" of multiple inheritance by reusing code across multiple class hierarchies without actual inheritance. A mixin defines capabilities "mixed in" to any class using with. Mixins can't be instantiated and (by default) can't have their own constructors.

mixins.dart
mixin CanFly {
  void fly() => print('Flying!');
}
mixin CanSwim {
  void swim() => print('Swimming!');
}
class Animal {
  void breathe() => print('Breathing');
}

// Duck can fly AND swim — no multiple inheritance needed
class Duck extends Animal with CanFly, CanSwim {}

void main() {
  final duck = Duck();
  duck.fly(); duck.swim(); duck.breathe();
}
🎯 Interview Question
Q: What is the difference between a mixin and an abstract class?
An abstract class defines a contract for "is-a" relationships and can only be single-extended. A mixin provides reusable "has-ability" behavior that can be plugged into any class — you can apply multiple mixins to the same class.

Async Programming
Theory

Dart is single-threaded but handles concurrency via an event loop. A Future represents a value (or error) available at some point in the future. async/await let you write asynchronous code that reads like synchronous code, while try/catch/finally handles errors.

Call async fn
→
Future<T> returned
→
Event loop continues
→
await resolves value
async.dart
Future<String> fetchUser() async {
  await Future.delayed(Duration(seconds: 2));
  return 'Shatrudhan';
}

void loadData() async {
  try {
    final user = await fetchUser();
    print('Hello $user');
  } catch (e) {
    print('Error: $e');
  } finally {
    print('Done');  // always runs
  }
}

// Run multiple futures in parallel
final results = await Future.wait([fetchUser(), fetchUser()]);
🎯 Interview Question
Q: Does await block the main thread while waiting?
No. await suspends the current async function and yields control back to the event loop, which keeps processing other events (UI rebuilds, gestures). It does not block the isolate's single thread.

Streams
Theory

A Stream is a sequence of asynchronous events, unlike Future which resolves once. Streams come in two flavors: single-subscription (one listener, used for discrete sequences like file reads) and broadcast (multiple listeners, used for ongoing events like UI state or sensor data).

streams.dart
// ── GENERATOR FUNCTION (async*) ───────
Stream<int> countDown() async* {
  for (int i = 5; i >= 0; i--) {
    await Future.delayed(Duration(seconds: 1));
    yield i;
  }
}

void main() async {
  await for (final val in countDown()) {
    print(val);
  }

  // .listen() with all callbacks
  countDown().listen(
    (val) => print(val),
    onError: (e) => print('Error: $e'),
    onDone: () => print('Complete!'),
  );

  // StreamController for manual control
  final controller = StreamController<int>.broadcast();
  controller.sink.add(1);
  controller.close();  // always close to avoid leaks
}
🎯 Interview Question
Q: What happens if you try to listen twice to a single-subscription stream?
It throws a StateError — single-subscription streams allow exactly one listener. Use .asBroadcastStream() or a StreamController.broadcast() if multiple listeners are needed.

Isolates
Theory

Dart code runs in a single-threaded isolate with its own memory — that's why a heavy synchronous computation freezes the UI even though Dart is "async." Isolates give true parallelism: each isolate has its own memory heap and communicates with others only via message passing (no shared state, no locks).

isolates.dart
// ── FLUTTER'S compute() — simplest way to use an isolate ──
int heavySum(int n) {
  int total = 0;
  for (int i = 0; i < n; i++) total += i;
  return total;
}

void runHeavyTask() async {
  final result = await compute(heavySum, 100000000);
  print(result);  // runs off the UI thread, no jank
}

// ── RAW Isolate.spawn ──────────────────
void worker(SendPort sendPort) {
  sendPort.send('Done from isolate');
}
void main() async {
  final receivePort = ReceivePort();
  await Isolate.spawn(worker, receivePort.sendPort);
  receivePort.listen((msg) => print(msg));
}
🎯 Interview Question
Q: When would you reach for an isolate instead of just using async/await?
async/await handles I/O-bound waiting (network, disk) without blocking — it doesn't run code in parallel. Use an isolate (via compute()) for CPU-bound work — JSON parsing of huge payloads, image processing, encryption — where the computation itself would otherwise freeze the UI.

Error Handling
Theory

Dart distinguishes between Exception (expected, recoverable problems — bad input, failed network call) and Error (programming bugs — null assertion failures, out-of-range index). Use try/on/catch/finally to handle exceptions, and create custom exception classes for domain-specific errors.

error_handling.dart
// ── CUSTOM EXCEPTION ───────────────────
class ApiException implements Exception {
  final String message;
  final int statusCode;
  ApiException(this.message, this.statusCode);

  @override
  String toString() => 'ApiException($statusCode): $message';
}

void fetchData() {
  try {
    throw ApiException('Not found', 404);
  } on ApiException catch (e) {
    print('API failed: $e');     // specific catch
  } catch (e, stackTrace) {
    print('Unknown error: $e');    // generic fallback
  } finally {
    print('Cleanup complete');
  }
}
🎯 Interview Question
Q: What's the difference between Exception and Error in Dart?
Exception represents expected failure conditions you should catch and handle gracefully — like a failed API call. Error represents programming mistakes (e.g., RangeError, TypeError) that generally shouldn't be caught — they indicate a bug that needs fixing, not a recoverable runtime condition.

Enums
Theory

Enums represent a fixed set of constant values. Since Dart 2.17, enhanced enums can have fields, constructors, methods, and even implement interfaces — turning what used to be a plain label into a small, type-safe data class.

enums.dart
// ── BASIC ENUM ─────────────────────────
enum Status { pending, approved, rejected }

void printStatus(Status s) {
  print(s.name);    // 'pending'
  print(s.index);   // 0
}

// ── ENHANCED ENUM (Dart 2.17+) ─────────
enum Plan {
  free(0, 'Free Tier'),
  pro(499, 'Pro Tier'),
  enterprise(4999, 'Enterprise');

  final int priceInRupees;
  final String label;
  const Plan(this.priceInRupees, this.label);

  bool get isPaid => priceInRupees > 0;
}

print(Plan.pro.label);       // Pro Tier
print(Plan.pro.isPaid);     // true
for (final p in Plan.values) print(p.label);
🎯 Interview Question
Q: When would you reach for an enhanced enum over a plain class?
When you have a small, fixed, known-at-compile-time set of values that each carry constant data — like subscription tiers, HTTP method types, or app environments. Enums guarantee exhaustiveness in switch statements, which plain classes can't.

Records
Theory

Records (Dart 3+) are lightweight, anonymous, immutable aggregate types that group multiple values without needing to define a class. They're perfect for returning multiple values from a function and can be positional, named, or both.

records.dart
// ── POSITIONAL RECORD ──────────────────
(int, String) getUser() {
  return (1, 'Shatrudhan');
}
final (id, name) = getUser();   // destructuring
print('$id - $name');

// ── NAMED RECORD ───────────────────────
({int age, String city}) getProfile() {
  return (age: 23, city: 'Ranchi');
}
final profile = getProfile();
print(profile.city);     // Ranchi — field access

// ── EQUALITY ────────────────────────────
print((1, 2) == (1, 2));   // true — value-based equality
🎯 Interview Question
Q: When should you use a Record instead of a class?
Use a record for short-lived, structural groupings — like returning two or three values from a function — where you don't need named identity, methods, or inheritance. Use a class when the type needs behavior, validation, or represents a meaningful domain entity.

Pattern Matching
Theory

Dart 3 introduced patterns: a way to match and destructure data in switch statements/expressions, if-case, and variable declarations. Combined with sealed classes, the compiler can enforce exhaustiveness — every possible case must be handled.

patterns.dart
sealed class Shape {}
class Circle extends Shape { final double radius; Circle(this.radius); }
class Square extends Shape { final double side; Square(this.side); }

double area(Shape shape) => switch (shape) {
  Circle(radius: var r) => 3.14 * r * r,
  Square(side: var s)   => s * s,
  // no default needed — compiler knows these are ALL the subtypes
};

// ── if-case ──────────────────────────────
final point = (3, 4);
if (point case (var x, var y) when x == y) {
  print('Equal coordinates');
}
🎯 Interview Question
Q: What does sealed buy you that abstract doesn't?
A sealed class restricts all direct subtypes to the same library. This lets the compiler verify exhaustiveness in a switch — if you add a new subtype later and forget to handle it in a switch, you get a compile-time error instead of a silent runtime bug.

Factory Constructors
Theory

A factory constructor doesn't always create a new instance — it can return a cached/existing instance (singleton pattern) or a different subtype based on input. This is impossible with a regular generative constructor, which always creates a brand-new instance of exactly its own class.

factory.dart
// ── SINGLETON via factory ───────────────
class ApiClient {
  static final ApiClient _instance = ApiClient._internal();
  ApiClient._internal();           // private named constructor

  factory ApiClient() {
    return _instance;             // always returns the same instance
  }
}
print(identical(ApiClient(), ApiClient())); // true

// ── fromJson — common in API integration ──
class User {
  final String name;
  User(this.name);

  factory User.fromJson(Map<String, dynamic> json) {
    return User(json['name'] as String);
  }
}
🎯 Interview Question
Q: Why can't a factory constructor access "this"?
A factory constructor doesn't necessarily create a new instance — it may return a cached object or a different subtype — so there's no guaranteed "current instance" to refer to. It behaves like a static method that happens to be called with constructor syntax.

Memory Management
Theory

Dart uses a generational garbage collector: most objects are short-lived and collected quickly from a "young generation" using a fast scavenger; objects that survive get promoted to an "old generation," collected less often with a mark-sweep algorithm. In Flutter, the most common memory leaks come from forgetting to dispose controllers, subscriptions, and listeners.

Allocate (young gen)
→
Survives GC?
→
Promoted (old gen)
→
Mark & sweep collected
memory.dart
// ── COMMON FLUTTER LEAK SOURCES ───────
class _MyPageState extends State<MyPage> {
  late final AnimationController controller;
  StreamSubscription? subscription;

  @override
  void initState() {
    super.initState();
    controller = AnimationController(vsync: this, duration: Duration(seconds: 1));
    subscription = someStream.listen((_) {});
  }

  @override
  void dispose() {
    controller.dispose();        // ✓ release animation resources
    subscription?.cancel();    // ✓ stop listening, avoid leak
    super.dispose();
  }
}
🎯 Interview Question
Q: What are the most common causes of memory leaks in a Flutter app?
Forgetting to call dispose() on AnimationController/TextEditingController, not cancelling StreamSubscriptions, holding a BuildContext reference after a widget is unmounted, and registering listeners (e.g. on a singleton) without removing them when the widget is destroyed.

Functional Programming
Theory

Dart supports functional-style programming via first-class functions and a rich set of higher-order methods on collections — map, where, reduce, fold. Chaining these creates concise, declarative data pipelines instead of manual loops.

functional.dart
// ── MAP / WHERE / REDUCE / FOLD ───────
final nums = [1,2,3,4,5];

final doubled = nums.map((n) => n * 2).toList();
final evens   = nums.where((n) => n % 2 == 0).toList();
final sum     = nums.reduce((a, b) => a + b);          // fails on empty list
final total   = nums.fold(100, (acc, n) => acc + n);  // safe on empty list

// ── CHAINING ─────────────────────────
final result = [1,2,3,4,5,6]
  .where((n) => n % 2 == 0)
  .map((n) => n * n)
  .toList();
print(result);  // [4, 16, 36]
🎯 Interview Question
Q: What is the difference between reduce and fold?
reduce combines elements starting from the first — it throws on an empty list. fold takes an explicit initial value, so it works on empty lists and can change the result's type entirely.

Interview Questions — Rapid Fire
Theory

A compiled set of the most commonly asked Dart questions across all chapters above — useful for a final review pass right before an interview.

Q: What makes Dart good for both client (Flutter) and server-side use?
It compiles to native ARM/x64 (AOT) for fast startup and performance, and to JIT for fast hot-reload during development — plus it compiles to JavaScript for web. A single language across mobile, web, desktop, and server.
Q: What is tree shaking and why does it matter for Dart/Flutter apps?
Tree shaking removes unused code at compile time, keeping release app size small — especially important since Flutter ships its own rendering engine.
Q: Difference between == and identical()?
== checks logical/value equality (can be overridden). identical() checks if two references point to the exact same object in memory.
Q: What's the difference between a top-level function and a static method?
A top-level function lives outside any class, directly in a library. A static method belongs to a class's namespace but doesn't need an instance to be called — useful for grouping related utilities.
Q: What is the cascade operator (..) used for?
It lets you call multiple methods/set multiple properties on the same object without repeating the variable name — e.g. Paint()..color = Colors.red..strokeWidth = 2.
Q: What does covariant mean in Dart?
It relaxes a type check when overriding a method, allowing a subclass to accept a more specific parameter type than the parent's signature declares — used when you're confident of the actual runtime type.
